# 文档规范

本文定义仓库内 Markdown 文档的职责、写法和维护规则。目标是让读者能快速找到规范来源，并让代码、配置和文档在变更后保持一致。

## 目录职责

| 位置 | 内容 | 规范来源 |
|---|---|---|
| `README.md` | 项目定位、支持边界、最短使用路径和文档入口 | 否；只导航 |
| `docs/requirements/` | 业务规则、范围、稳定需求编号 | 是，业务需求 |
| `docs/ui/` | 页面信息架构和交互规则 | 是，UI 要求 |
| `docs/acceptance/` | 可观察的验收场景 | 是，验收条件 |
| `docs/explanation/` | 架构、边界与设计理由 | 是，设计说明 |
| `docs/guides/` | 开发、部署、备份恢复等可执行操作 | 是，操作步骤 |
| `docs/reference/`、根目录 `COMPATIBILITY.md`、`locks/` | 目录布局、兼容性、镜像和依赖等精确事实 | 是，各自领域事实 |
| `docs/releases/`、`CHANGELOG.md` | 已发布版本的变化与升级影响 | 是，发布历史 |

## 写作规则

- 一篇文档只回答一种问题；需求、设计理由、操作步骤、发布历史不得混写。
- 每项事实只保留一个规范来源。其他文档使用链接说明，不复制版本、镜像 digest、环境变量默认值或命令细节。
- 操作指南以可按顺序执行的步骤组织，标明前置条件、风险、验证命令和恢复/回退边界。
- 需求使用稳定的 `REQ-*` 编号；验收应给出可观察输入、动作和结果，优先对应自动化测试。
- 设计文档说明“为什么”和约束；不记录瞬时执行状态或逐步命令。
- 发布说明只描述该版本已经发生的变化，历史文件不因目录重构而改写其当时的叙述。
- 示例中不得出现真实密钥、生产数据、数据库备份或内部地址。

## 变更同步

| 变更 | 必须同步更新 |
|---|---|
| 用户可见行为 | 对应需求、验收场景、测试与 `CHANGELOG.md` |
| 数据模型或迁移 | 需求/架构、迁移与升级恢复说明、发布说明 |
| 环境变量、端口、卷或命令 | 对应操作指南与唯一参考来源 |
| NetBox、依赖或镜像版本 | `COMPATIBILITY.md`、`locks/`、发布说明和受影响指南 |
| 文档移动或重命名 | `README.md`、`docs/README.md` 及全仓库 Markdown 链接 |

提交前至少执行 `git diff --check`，并检查受影响 Markdown 链接。代码或配置变更不能仅更新 README 而遗漏其规范来源。
